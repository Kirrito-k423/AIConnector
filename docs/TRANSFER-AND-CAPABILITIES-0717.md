# 0.7.17：传输分块与能力公告修复

对应 [Issue #20](https://github.com/Kirrito-k423/AIConnector/issues/20) 和 [Issue #21](https://github.com/Kirrito-k423/AIConnector/issues/21)。

## 文件上传

Windows 新建文件传输改为最多 **768 KiB 明文 / 块**。实际 age 加密及 ZIP 封装完成后还检查单块 `< 1,000,000` 字节，包含加密和封装开销，给十进制 1 MB 和二进制 1 MiB 的出站限制留出余量。不可压缩随机数据也须通过该检查。无需更改用户配置或重新配对。

`file-transfer-v1` 的密文绑定、SHA-256、逐块 offset、断点续传及最终索引格式不变。写入分块尺寸与读取兼容上限分离：升级后的 Mac 仍能读取历史 3 MiB 明文块；旧 Mac 的 v1 读取端也能接收新的小块。推荐两端升级同版。

### 恢复旧的超限运行

1. 先升级 Windows 接收服务，确认运行版本为 0.7.17。
2. 对已经生成 `sealed` 索引的旧运行，**重新发送同一个 runKey、重启服务或执行 `RetryRejected` 都不会重新切分**。密文及内容寻址名称已经冻结，不能在原运行内替换成新的文件快照。
3. 发起一次新的文件传输：保留 task_id 时，**增加任务 revision，并使用新的 run_id**；也可以直接使用全新的 task_id。发送端重新生成绑定新 runKey 的加密请求，不能复用旧请求 ZIP。由于加密请求的 SHA 也属于不可变任务定义，仅更换 run_id 会触发 `REVISION_IS_IMMUTABLE`。无需更改 `code.revision=file-transfer-v1`。
4. 对明确已完成读取、仅上传失败的旧任务，新运行会按新尺寸重新读取当前文件，可能得到新的文件版本；原运行和上传证据保留。仍在执行或执行状态未知的任务，应先核实，不能冒充本次已完成读取。

稳定重现的代理大小 403 不做无限盲重试，也不把所有 403 当成网络波动；权限类拒绝保持原行为。本次不拆分或重写已发布的资产。最终结果索引仍受既有格式限制（公开索引 256 KiB / 4096 块、加密文件清单 3 MiB）；768 KiB 是数据块策略，不宣称任何规模的最终索引都能穿过所有代理。

## 能力公告

根因除了 `Advertise:6`，还包括其被标为 `background`：实际排队 rank 固定为 8，优先级数字和等待老化均不生效。因此仅修改 `Advertise:1.5` 不足以保证修复。

- Advertise 退出后台分类，初始优先级位于 Upload 与 FetchTransferPart/Submit 之间。
- 等待达到 **60 秒**或被 **12 次前台调度**越过后，在请求结束边界获得公平执行机会。Poll 保留 **10 秒 / 4 次**规则；同时到期时按等待期限排序，两者都能进展。
- 正在执行的 HTTP 请求不会被中断。这是队列调度预算，不是公网发布的 60 秒硬 SLA；正在执行的慢请求、断网、GitHub 限流及退避仍可延长实际交付。
- 真正出队时重新采集当前能力，不把排队前旧配置换时间后冒充新快照。
- 接收端本地记录采用远端确认公告的 `generated_at`，不能用“刚读到确认”的时间延长公告寿命。内容相同时约 30 分钟刷新；发送端仍拒绝超过 2 小时的公告。没有每 30 秒重复发同一条评论。
- 同一服务最多一个待处理公告；原有不确定写入查询及重试机制保留。审计和诊断仍为尽力执行的后台动作。时序记录增加 `advertise_fair_turn`，便于核对排队耗时。

## 验收范围

回归涵盖：不可压缩数据经过真实加密封装后的大小及逐字节解密、历史 3 MiB 块读取与封存索引保留、Windows/Mac 断点恢复、公告在长前台积压下的次数与时间界限、公告与 Poll 同时到期、出队时能力变化、采集失败后队列继续、公告生成时间不被确认时间延后。

Mac 和 Windows 安装包必须从新解压目录运行测试；Windows 继续执行 PowerShell 5.1、丢失响应/限流、维护恢复、并行及性能验收。CI 的代理尺寸模拟不等于已在内网公司的真实代理复测；后者需升级后的新传输运行确认。无需为这两个修复更改 simpleHtmlWatch 中台。
