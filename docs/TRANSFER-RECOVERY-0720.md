# 0.7.20：失败上传占位恢复与并发证据保留

## 现场事实

0.7.19-rc.1 的同批四文件复测运行 `transfer-benchmark-20261019/1/run-eight-01`，见 [Relay #52](https://github.com/Kirrito-k423/AIConnector-Relay/issues/52)。Windows 能力公告恢复，四文件最终完整取回 Mac：73,951,932 字节，逐文件字节数与 SHA-256 均与旧批次相同，未排除文件。

回传停在 96/97 分块时，Windows 报 `ASSET_CONFLICT`。Release 概览只显示已完成附件；直接列举 Release assets 发现另一个同名分块占位：`state=starter`、无 digest、声明大小 787,273 字节、更新时间长期不变。声明大小不能证明对象已完成。代码将这条失败占位当成不可恢复的完整附件冲突。

[GitHub 官方接口文档](https://docs.github.com/en/rest/releases/assets#upload-a-release-asset)说明，上游上传失败可能留下可清理的 `starter` 记录。现场没有保存最初失败响应，不能据此断言本次最初一定返回了 HTTP 502，也不能将先前的 `CHANNEL_COOLDOWN` 全部归因于并发限流。

2026-10-19 20:13:39 北京时间，再次核验该占位已停留 10,140 秒、没有摘要及下载记录后，只删除了 asset `655813475`，并确认 404。原运行自动续传；未重建任务、未删除其他分块、未清空退避。末块于 20:15:11 创建，20:17:04 回执，20:24:31 Mac 完成下载解密及完整性校验。

## 修复行为

1. 只处理已验证运行中、内容寻址名称一致、存在本地持久上传意图的 `starter`；无摘要，声明大小须为零或与本地一致。
2. 本地上次上传和远端最后更新时间均超过等待期（至少 120 秒，且不小于两倍请求超时/轮询周期）；跨重启保留观察记录。
3. 两次观察相隔至少一个轮询周期；清理前再次 GET 精确 asset ID。若已经完成则走原有完整性校验，绝不删除。
4. DELETE 遵守全局写入节流和服务端退避。丢回复后按同一 asset/run 核对；确认缺席后才续传。有效文件摘要不符仍报错，不覆盖数据。
5. 原生 HTTP 开始/结束计时另存到按运行键哈希命名的本地文件。每次上传尝试两条记录，无额外轮询或网络请求；每运行当前/上一份各 2 MiB。诊断新增 `transfer_events`、截断/轮转标记，最多导出 4,000 条；分析仍须对照最终索引检验覆盖率。旧版本缺失的计时无法补回。
