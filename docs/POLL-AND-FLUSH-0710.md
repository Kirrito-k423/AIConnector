# 0.7.10：任务发现独立排队，降低本地 Flush 开销

0.7.8 的回传事件显示：上一轮 Poll 返回后，下一轮约 14 分 29 秒才入队，中间 23 项串行操作占用约 99.8% 的区间。其中 11 次 Flush 共 547.6 秒、5 次 Upload 共 165.4 秒。原五项平均发现等待 386.1 秒由后两项约十五分钟的等待拉高。这是历史观测，不是 0.7.10 的性能结果。

## 调度变化

- 到期 Poll 不再等待 Flush、其他任务 start/delivery 或前台待执行队列清空。服务 busy 标记覆盖排队和执行；传输层也合并重复 Poll 调用，最多一个待执行或正在执行的请求。
- 前台操作保持原有优先级；Poll 排队达到 10 秒或被越过 4 次后，在下一次请求边界获得执行机会。此预算是公平调度条件，不是发现延迟硬上限；当前在途慢请求仍须完成。
- Poll 结束后仍按配置间隔再次检查。10 秒采样只写本地，不增加周期网络上传；平台冷却、鉴权、完整分页、协议验证及上传对账继续生效。
- 机器锁和 Pi 并发上限仍在任务已发现/登记后的执行阶段检查。排队 Poll 不会释放机器、重复 Claim 或重放实验。

## Flush 的本地工作

Save 将整个本地账本一次性转换为 JSON，替代对每个字段递归排序和单独转换。aiconnector.store.v1 继续保存 exact-byte SHA-256、base64 数据、原子替换及 durable flush。旧版读入和重启格式兼容；事件、协议 payload、event_id、产物 SHA 继续使用原有规范化与校验规则。

Snapshot 比较缓存前先保存当前内存状态，避免以旧 SavedStateHash 返回旧投影；生成投影时新发现的冲突也会在返回前保存。状态和投影没有变化时不重复落盘。

自动转换中，成功入队由 Queue 自己持久化；没有转换的轮次不再额外序列化整个账本。失败的产物验证仍保存错误状态，快照仍保存新发现的冲突。此前 Windows 小账本对比暴露重复 Save 的固定开销，因此额外保存检查与这项去冗余一起验收。

## 验证和部署

新增回归覆盖：Flush/Upload 阻塞时 Poll 仍入队；只有一个 Poll；成功/失败后释放该槽；持续旧前台积压下 4 次越过预算；10 秒到期后的边界调度；本地账本中 Unicode、时间字符串、空/单元素数组、布尔、null、大整数及分数的保存和重启。既有资源互斥、领取所有权、丢回复恢复和接收端产物校验回归继续运行。

配对基准：`PWSH=<PowerShell> python tools/benchmark_flush.py --baseline <0.7.9 Connector.ps1> --output <report.json>`。在相同合法的 1/40 项闭环账本上，各取 3 对交错样本，使用真实常驻 PowerShell，保持相同投影、文件无重写、网络请求为零。这只测有历史账本时无新消息的 Flush 本地成本，不代表公网写入、内网代理或 A5 端到端收益。

Mac arm64 / PowerShell 7.6.6 的上述主机样本中位数：1 项账本从 37.3 ms 降至 25.6 ms；40 项账本从 828.5 ms 降至 402.1 ms（降低约 51.5%）。[原始配对样本](evidence/flush-0710-macos.json)同时保留两版源码 SHA、零网络请求和文件无重写证明。Windows PowerShell 5.1 另在发行 CI 中运行同口径基准，不能由 Mac 数字推算内网收益。

升级两端时使用已有配置和状态。Windows 验收应确认连续交付其他任务期间，到期 Poll 已排队并实际获得执行；被占用机器仍显示 RESOURCE_BUSY。不得清锁或重放未知实验。早期十秒窗口仍有保留上限，性能验收需要及时导出覆盖任务发布/发现时段的证据。
