## 实现

Windows 文件传输默认最多 **2 个在途数据 POST**。配置为 `runner.transferConcurrency`，范围 1–4；1 可作为串行回退。无需新配对、增加模型或更改 simpleHtmlWatch。变更本地配置后重启服务生效；按原升级规则先确认没有活动执行器，不重放未知任务。

数据 HTTP 由原生 .NET 的异步 I/O 执行，复用原 Windows 系统代理、TLS 和 HTTP 连接池。没有为每块启动 PowerShell，也没有让多个进程同时写入同一状态文件。原 PowerShell 常驻进程继续独占状态、先持久化上传意图，再启动 I/O，最后按顺序确认；Node 侧使用跨任务共享的有界队列。文件读取、任务 Claim、SSH 实验和资源锁不改变。

上传进行时，常驻进程可以处理 Poll、Claim、完成事件及能力公告。异步完成查询只读取进程内状态，避免重建全部任务和反复落盘。完成查询不访问公网，也不产生高频成功日志；每块保留启动、真实 HTTP 时长和确认记录。`transfer_part_http_finished.elapsed_ms` 由原生异步请求计时，不把等待下一次状态查询的时间算作网络耗时。并行 HTTP 的时长存在重叠，不能相加当作端到端耗时。

已经校验的 Release 身份和完整附件目录短暂复用，缓存不持久化、命中不续期，鉴权变化或远端错误会失效。本地写入间隔、队列容量及尚未到期的核对等待不清缓存，避免每次等待都重新查询；缓存仍按原 30 秒期限失效。只有从未发出过的新上传可复用目录中的缺席观察；不确定写入必须查新目录。422 同名竞争强制刷新，并对既有资产进行字节哈希核验，绝不覆盖或删除。

原 `write_interval_seconds`（默认 3 秒）和全局限流退避保留。并发只允许请求跨越等待重叠，不允许跳过写入节流。若单次请求很快，受写入间隔约束时实际并发仍可能为 1。收到 429/限流 403 后停止发新 POST，并按服务器到期时间恢复；已在途且成功的兄弟分块仍可确认。普通 403 不盲重试。

另修复本地 `WRITE_COOLDOWN` 被执行器统一放大为至少 10 秒的问题。已知本地间隔按其到期时刻恢复；HTTP 故障、不确定投递和服务器限流仍按各自重试约束处理。

任意分块失败后，停止为该批次分配新工作，等待已启动请求完成并保存各自检查点。进程崩溃后查询原内容寻址名称，不能因回复丢失重发 POST。全部分块确认后才上传最终索引并发布 Result。旧的超限密文仍遵守 0.7.17 的不可变规则，不会通过并发重新切分。

## 测试和性能证据

`tests/test_transfer_pipeline.py` 走真实 Runner → 常驻 PowerShell → 延迟 HTTP 服务。4 个约 768 KiB 合成数据 ZIP，每次 POST 延迟 1 秒，最后上传结果索引；不访问内网、不读取真实私人文件。

旧 0.7.17 基线的首次复现：6.46 秒、峰值 1 路、附件列表查询 5 次。新版初始实现：4.28 秒、峰值 2 路、附件列表查询 1 次。后续增加了低开销完成查询和本地写入间隔修复，最终对照记录与原生 Windows 验收见发布说明。这些数值只证明受控路径改善，不等于该次内网 3 小时任务的提速比例。

回归覆盖全局并发上限、跨任务共享队列、上传期间控制请求进展、成功检查点保留、未收到的写入不盲重试、上传成功后丢回复/重启、429 后不发新数据、兄弟块收尾、422 竞争核验、写入间隔、最终索引顺序，以及两端安装包验收。Windows 必须使用 PowerShell 5.1 验证实际交付包中的原生异步模块。

[GitHub 官方建议](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)倾向串行请求并为写操作留出间隔，以避免二级限流。因此这里默认有界两路、保留写入节流与退避，并提供一路回退；没有承诺四路或更高并发一定更快。
